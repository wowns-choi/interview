## Project

"AI 면접 준비 도우미": given a job posting and a resume PDF, it extracts evaluation criteria, finds per-criterion evidence in the resume, and builds a personalized interview question sheet. Interviewers can record answers per question and download the sheet as a PDF. AI never makes hire/no-hire decisions; 「AI와 대화」 (user, 2026-10-28, formerly 「AI 의견 참고」) only answers the interviewer's questions about the material. The original spec is **`AI 면접 준비 도우미 구현 지시서.md`** (Korean), but the UI has since been simplified (see below).

## Architecture

Request flow: `controller/` → `service/` → `mapper/` (MyBatis interfaces + XML in `resources/mapper/`). JSPs live in `src/main/webapp/WEB-INF/views/` and share the `common/header.jspf` / `footer.jspf` static includes. Each page sets `activeTab` before including the header. Forms with `data-partial="#id"` (question extract/merge, interview record, AI opinion, report info/source) are posted with `fetch` by `app.js`; it parses the redirected page, swaps only the children of those elements (scroll stays put, user 2026-10-23: a full reload jumped to the top and restoring the scroll felt bad), shows the flash as a toast and fires a `partial` event so `extract.js`/`report.js` re-bind; a different redirect path falls back to a normal navigation.

**Flow** (`ExtractController`, `static/js/extract.js` on `positions.jsp` and `fit.jsp`). URLs: `/positions` (new position), `/positions/{id}` (criteria), `/fit?position={id}` (resume upload), `/results/{id}` (candidate id; evidence + questions), `/ranking?position={id}`.
1. `POST /positions` → `PositionService.create` + `extractCriteria` (AI ①; sets the title from `position_title`, stores the posting's `required_experience` and `required_education` verbatim (empty string from the AI = absent, stored as null), marks CONFIRMED; right after a successful extraction the flash `justExtracted` marks `.pos-grid[data-write]` and `initWriting` in `extract.js` types the conditions then criteria with a caret (the posting shows at once; user 2026-10-27 found typing it uncomfortable), any click or key finishing it (user 2026-10-27: they used to pop in all at once); criteria never carry years or education, e.g. "Java/Spring 기반 개발 경험" not "5년 이상", because the stamps compare those and AI ② once listed "총 2년 3개월" as DIRECT evidence for a 5-year criterion, which scored it full; `evidence.txt` also says to judge no years and to list only supporting evidence); the user can rename a position in place (pencil next to the title or on each list item on hover, `PATCH /positions/{id}`), which sets `position.title_edited` so a later re-extraction no longer overwrites the name. 경력·학력 conditions are always shown above the criteria (user 2026-10-27 layout: the posting as a tinted sheet; on the right 「지원 조건」 as three tiles 요구 경력 · 학력 · 학과 with the pencil, then 「평가 기준 n」 as a numbered 01, 02… list) (empty = 공고에 없음) and edited one cell at a time (a pencil per cell; picking a value saves at once, the major on Enter or blur, Esc cancels; user 2026-10-27) through dropdowns, not free text, per the user (경력: 공고에 없음/경력무관/N년 이상/N년 이하; 학력: 학력무관/고졸/초대졸(2·3년제)/대졸(4년제)/석사/박사 이상). `ConditionForm` reads the stored wording into the initial choices; the page saves fixed wording ("경력 3년 이하", "대졸(4년제) 이상") with `PATCH /positions/{id}/conditions` (blank = no condition). "N년 이하" (also 미만/까지/↓, e.g. "신입·경력 3년 ↓", user 2026-10-27) is a cap (`CareerGauge.meets`); that sets `conditions_edited` so re-extraction keeps them. EDUCATION_EVAL gets `position.required_education` as `<education_requirement>` (blank = no condition; the posting text is not sent); the career stamp reads the position field directly, so only the education stamp needs a re-check after an edit. Both are shown above the criteria and in the stage-② profile band. Criteria CRUD is JSON fetch under `/positions/{id}/criteria`.
2. Masking (`BatchCheckService` → `ResumeAnonymizer`; `ExtractionService.uploadResume` is the same reading + masking without the queue, now used only by tests; the old `POST /positions/{id}/resume` endpoint and the review editor were removed 2026-10-23, so the review-editor description below is history): takes any number of files (resume + portfolio; PDF, DOC, DOCX, PPT, PPTX, HWP, HWPX via `DocumentTextExtractor`; a .doc is sniffed by its bytes because 사람인·잡코리아 exports are HTML named .doc (OLE2 → POI HWPF, PK → docx, RTF → `RTFEditorKit`, HTML → jsoup with table cells joined by " | "); no count limit, only the per-file and request size limits). Every file is read before any AI call (a bad file saves nothing). With more than one file, texts are joined under `[첨부 n (형식)]` lines; file names are never put in the text because they often contain the applicant's name. **Rules to preserve:**
- **View models used from JSP must be classes with getters, not records.** Tomcat 11's EL exposes only record components, so derived getters like `getMatch()` would be invisible. That's why `ResultReport`, `CriterionEvidenceView`, `SectionView`, and `QuestionView` use Lombok `@Value`.
- **AI calls stay outside DB transactions.** Only DB writes are wrapped in `TransactionTemplate`.
- **`AiClient` is the single entry point for all AI calls.** `call` goes to the external OpenAI-compatible API; `callLocal` goes to Ollama's native `/api/chat` (OpenAI-compatible mode can't set `num_ctx`, so long resumes would be silently cut; a call that reaches `num_ctx` fails).
  - It strips code fences, parses JSON with Jackson 3 (`tools.jackson.*`), and runs the DTO's `validate`.
  - It retries **exactly once** with the error appended, then throws `AiCallException`.
  - Every attempt is logged to `ai_call_log` via `AiCallLogger`, which uses `REQUIRES_NEW`.
  - The `ai.trace` logger (user request) prints every GPT and local AI request (`[GPT 요청]`, `[로컬 AI 요청]`: all messages; images only as a count) and response, pretty-printed, to the console. Local requests and responses contain the raw PII. `logging.level.ai.trace` turns it off (OFF in tests).
  - The user pays for GPT: verify with stubbed tests or local-only runs, and make real GPT calls only when truly needed.
- **Evidence IDs sent to AI ③ are 1-based list positions** in the saved evidence list. `AnalysisService.extractQuestions` and `mergeQuestions` map them back to real IDs. The assembler drops unknown IDs instead of guessing.
- **Question sheet order (initial):** the ③-2 arrangement plus the gap filling above; "기타" is used only when there is no anchor at all. After that the user can reorder freely. `origin=FIXED` only exists in old rows and is shown as 공통; `MANUAL` is a user-added question.
- **Prompts are files** (`resources/prompts/*.txt`), read on every call.
  - Untrusted input is wrapped in tags (`<resume>`, `<job_posting>`, …) and declared as data, not instructions.
  - The candidate's name and unmasked resume text are never sent to the external AI.
- **Hidden vs. sent (user's rule).** Never sent to the external AI: name, age, gender, contact, email, address, links, employer, rank, salaries, education, desired salary, training. Sent (evidence): certificates (user, 2026-10-22), career periods (재직 기간, 근무 기간, 총 경력; unmasked since 2026-10-21 per the user, because AI ② needs them for the career count and they were sent anyway), work/project content and results, tech stack, project names and dates, client companies, team names, cover letter. Labels: `[이름] [전화번호] [이메일] [주민번호] [링크] [생년월일] [주소] [개인정보] [회사] [A사] [B사]… [연봉] [경력] [학교] [학력] [교육]` (`[자격증]` only in old texts). `evidence.txt` tells AI ② to mark criteria that need hidden facts (degree, training) as NONE and point to the summary at the top. - **PII masking is done by the local AI; regex is only a backstop.** `ResumeAnonymizer.normalize` first turns PDF special spaces (U+00A0 etc.) and full-width ASCII into plain characters; without it, Java `s` misses NBSP and values like "3,400 만원" never match. (Not NFKC: it would rewrite Korean compatibility jamo like "ㆍ".) `PiiExtract.validate` fills missing fields with empty values and never fails, and swaps a career's 재직 기간 and 근무 기간 when only the latter holds a date (gemma4 mixed them up; the prompt also gives examples now). `PiiMasker` matches every value ignoring whitespace and case, because the model often re-spaces what it copies ("3,400만원" vs "3,400 만원"). `ResumeAnonymizer.LABELED` covers fixed shapes the model misses intermittently: age, the postal code after "주소", the date after "생년월일", the rest of a "주소" line starting with a 시·도 name, amounts after "연봉", GPA, "대학교(4년)"/"(2·3년제)", the "인정학력" line, and the value after a 장애/보훈/병역 field ("병역 : 군필", "장애여부 해당 없음"; a bare label needs a colon so prose like "병역 특례 업체" is untouched; military-table values written with spaces only: service status and type words (병역필, 군필, 만기제대, 의무경찰, 사회복무요원…) anywhere, ranks after 계급 or in parentheses ("수경(병장)"), the value after 군별/역종/병과/주특기/군번/제대·전역·복무 구분 (label followed by a space or colon, so "특기사항", "주특기는" stay) and a same-line 면제 사유). Age/birth date/address/salary values are masked everywhere; the education patterns and the 장애·보훈·병역 values are masked only where they match (`maskLabeled`, after value masking so the full address still matches first). `PiiLeakChecker.maskObvious` then masks any RRN/phone/email shapes still left (the local AI intermittently misses a second number such as an emergency contact), and `find` rejects leftovers (after NFKC normalization; it is also the check on user-edited text at the review step). The resume text goes only to the local AI before masking.
- **Profile (인적사항·경력·학력·교육·자격증) is shown, never sent.** **One form, no stated purpose (user, 2026-10-21):** the local AI is only asked to find and copy values into Korean-keyed fields (`PiiExtract`: 이름[], 다른 사람 이름[], 성별, 생년월일[], 연락처[], 이메일[], 주소[], 링크[], 학력[{학교,전공,상태,기간,학점}], 경력[{회사[] (every spelling), 부서, 직급, 재직 기간, 근무 기간}], 총 경력, 연봉[], 교육[], 자격증[], 활동[], 기타 개인정보[]); the prompt never mentions masking or what may be sent. The earlier prompt asked for "items to mask" plus a "profile", and gemma4 read it as "filter sensitive values out" and left both nearly empty (only the name), leaking companies, school, email and link. Code derives both uses: `PiiExtract.toItems()` masks every value except the department and career periods (재직 기간, 근무 기간, 총 경력; rank is still masked as `[경력]`; activities only for 병역), `toProfile()` builds the display profile (first spelling of each single field, no salary). `ResumeAnonymizer` merges chunks, drops profile values not found in the original text (whitespace-insensitive). `anonymize` runs five steps in order: 1) detect and merge (profile verified), 2) `byCompany` + `aliasCompanies`, 3) `maskList` (every found value, company names also without "(주)"-style legal forms, companies labeled by alias), 4) mask, 5) return for saving. `byCompany` folds careers of the same company into one row (first non-empty value per field, so the summary table's period wins over the per-project 근무기간 blocks of a 경력기술서). `aliasCompanies` then stores `alias` ("A사", "B사"… in career-list order) on each career and masks each listed company (with and without its legal form) as `[A사]`, `[B사]`…; every external call and `TimelineView` use that stored alias, so the external AI can tell which work belongs to which company; other spellings of the same company (`PiiExtract.companyNames`) get the same letter, and any other company label stays `[회사]`. In the same step `aliasOthers` stores `alias` "학교1", "교육1", "활동1" (list order) on education, trainings and activities (user, 2026-10-21: every alias is saved with the profile, none is derived at request time; old profiles without aliases are not supported and the DB was reset). The review editor's label regex in `extract.js` knows these labels. It is stored as `candidate.profile_json` (so contact details are in our DB) and shown read-only in stage ② after the fit check and in the PDF, next to the posting's required experience. The profile also has `activities` (병역, 연수, 인턴, 회사 밖 프로젝트: kind + name + period, for the timeline; only 병역 values are added to the mask list). Keep `pii_detect.txt` short: a longer activities instruction once made gemma4 drop birth/address/phone/email in 4/4 runs. **Salaries are masked but not kept (user, 2026-10-21):** PII_DETECT copies every salary into 연봉[] so it is masked (with the SALARY `LABELED` patterns as backstop), but `toProfile` never puts salaries in the profile. Old profiles may still hold salary values; nothing reads them. (A separate SALARY_EXTRACT local call existed briefly and was removed with salary evaluation.) The `ai.trace` log prints every local call's `thinking` as `[로컬 AI 생각]`. gemma4:26b was tried on 2026-10-20: one chunk took 4m40s, filled `num_ctx` 8192 with thinking and returned nothing, with RAM at 98%; e4b stays. **Career/education calculation (both at the fit check, user's split):** total career needs the resume body (the user treats "총 경력" as position-relevant), so AI ② (`evidence.txt`) gets only `기준 월`, the posting (for the job type), the criteria (id, name, description) and the masked resume, where periods are visible next to `[A사]` (no separate career list and no required-experience line, per the user), and returns `career` (per_company first, then total months with overlaps counted once and relevant months; `EvidenceResult.validate` requires it). Two parallel resume-less calls replaced the single CAREER_EVAL (user, 2026-10-21; the enum value stays only for old log rows): EDUCATION_EVAL (`education_eval.txt`, `CareerEvalService.education`, reasoning model) sends only "학교명 | 상태 | 기간" lines and the position's `required_education` (plus `<major_requirement>` and a 전공 column when `position.required_major` is set: 학과 condition, user 2026-10-22, extracted by AI ① as `required_major` or typed in the conditions editor as free text; `education_meets` then covers both), and returns `final_education`, `education_reason`, `education_meets` (skipped when there are no schools; forced to UNKNOWN when there is no condition); TIMELINE (`timeline.txt`, `CareerEvalService.timeline`, default model) sends only `기준 월` and "A사 / 학교1 / 교육1 / 활동1 | 기간" lines (no names or activity kinds) and returns each label → YYYY-MM start/end (unreadable ones are dropped, not failed). Prompts are kept as short as accuracy allows (user). `CareerEvalService.save` merges all three into `CareerEvalResult`; a failed call keeps its previously saved fields. `TimelineView` maps the stored aliases back to real names, skips careers the external AI did not count in `per_company` (`CareerEvalResult.counts`; the local AI sometimes lists a client company or project as a career, user 2026-10-22; the 경력 상세 dialog lists only companies with relevant months > 0, `ResultReport.getRelevantCareers`, user 2026-10-27; its summary reads only 포지션 관련 N; the 학력 상세 dialog has no AI reason line and, like the timeline, skips education rows with no school name (`Education.isLevelOnly`: "대학교", "고등학교"…, a 「최종학력: 대학교(4년) 졸업」 summary read as a school; EDUCATION_EVAL still gets them); the profile career list hides them too), and appends 「포지션 무관」 to a career whose `per_company` relevant months are 0 (`CareerEvalResult.unrelated`; user 2026-10-27: a café job read as just 경력), sets a minimum px width for the time axis so each label fits inside its bar (estimated from character widths, capped at `MAX_WIDTH`; the card scrolls horizontally and starts scrolled to the latest records, per the user who disliked cut-off "…" labels), puts the label beside any bar still too short, stacks overlaps including those outside labels, and marks months covered by nothing for 3+ months between the first record and today as "이력서상 기록 없음" (computed in code). All five lanes (경력·학력·교육·활동·기록 없음) are always shown, empty ones too (user wants it consistent). In the PDF the chart is hidden and the same items print as a plain list in start order regardless of lane (`TimelineView.getEntries`, `.tl-list`, user's choice after a vertical-axis attempt was rejected). The user wants the external AI, not code or the local AI, to do the career arithmetic and judgment. EVIDENCE and EDUCATION_EVAL use `ai.reasoning-model` (default gpt-5-mini, env `AI_REASONING_MODEL`; `AiProperties.modelFor`) with `ai.reasoning-max-tokens` (default 25000, since reasoning tokens count toward the cap; non-reasoning models such as gpt-4o-mini reject anything over 16384): in a 2026-10-19 comparison on fictional cases only reasoning models got the overlap arithmetic right (gpt-4o-mini 7/12, gpt-4.1 3/12, gpt-5-mini 12/12). On a real resume on 2026-10-20, gpt-5-mini's evidence quotes were 12/12 verbatim (≈47 s) vs gpt-4o-mini 3/6 with a missed AWS mention (≈6 s). The prompt makes it fill `per_company` first, which made the relevant-months judgment stable. **충족/미충족 stamps** (user request; per posting condition, not a hire decision): `RequirementFit` — career = CAREER_MEETS (user 2026-10-27, `career_meets.txt`, `CareerEvalService.careerMeets`, reasoning model): right after EVIDENCE, only the posting's experience text and EVIDENCE's relevant/total months and relevant reason are sent (no resume), returning `career_meets` MET/NOT_MET/UNKNOWN + `career_reason` (the career line tooltip), stored with the requirement it judged (`career_requirement`); `CareerEvalResult.careerVerdict` uses it only while the position's requirement is the same, else (older checks, or right after an edit) code compares relevant months with the posting's years (무관/신입 = met); editing the 경력 condition re-asks it for every ANALYZED/DONE candidate of the position on a background thread (`rejudgeCareer`); the compare-line sign follows the verdict; education = `education_meets` from EDUCATION_EVAL (the position's `required_education` is stored next to it). Red = 충족, blue = 미충족. It is stored in `candidate.career_eval_json`; a failure only leaves it null. `CareerGauge` draws total (light) and relevant (dark) career against the posting's years read by regex ("3~5년" → marker at the lower bound, 신입/무관 → no marker); `CareerGauge.meets` checks both bounds ("2년 이상 10년 이하", "3~5년" = in between; "N년 이하" = cap); before the check it falls back to the resume's verbatim total career.
- **JSP output escaping:**
  - Static JS/CSS URLs carry `?v=${applicationScope.assetVersion}` (server start time, `AssetVersionConfig`) so a restart never leaves the browser on old scripts; add it to any new script or stylesheet tag.
  - Escape all user and AI text with `<c:out>`.
  - Each `.jspf` needs its own `pageEncoding="UTF-8"`.
  - Session tracking is cookie-only, so URLs never get `;jsessionid`.
- **Test properties replace the main ones.** `src/test/resources/application.properties` fully shadows the main file, so add new required properties to both. Schema changes to existing tables go in `schema.sql` as idempotent `ALTER TABLE` statements valid in both PostgreSQL and H2; one-time seed data is guarded by `app_setting('seeded')` so deleted defaults don't come back.
