# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"AI 면접 준비 도우미": given a job posting and a resume PDF, it extracts evaluation criteria, finds per-criterion evidence in the resume, and builds a personalized interview question sheet. Interviewers can record answers per question and download the sheet as a PDF. AI never makes hire/no-hire judgments. The original spec is **`AI 면접 준비 도우미 구현 지시서.md`** (Korean), but the UI has since been simplified (see below).

**Deliberate deviations from the spec:**
- **Four tabs, per the user (2026-10-20), in this order:** `공통 질문 설정` (`/templates`), `평가 항목 추출` (`/positions`, also `/` and the old `/extract`; `positions.jsp`: list of positions on the left, the selected one on the right with posting text → editable criteria, or the new-position form), `포지션 적합도 검사` (`/fit?position=..` and `/results/{candidateId}`; `fit.jsp`: a position `<select data-nav>` (choose only; criteria shown as read-only chips, never created here), candidates on the left with their score, the selected candidate on the right: review editor, profile, evidence, then the interview question sheet at the bottom), `지원자 비교` (`/ranking?position=..`; `ranking.jsp`, `RankingService`: candidates by score with a per-condition/per-criterion cell grid; clicking a name opens `/results/{id}` in the fit tab with that position and candidate selected). Without `position` the latest position with criteria is used. No brand/logo in the top bar. The spec's masking-preview step was removed on purpose.
- **No 필수/우대 (user):** every criterion weighs the same. The `requirement` column is dropped in `schema.sql`, AI ① no longer returns it, and criteria are ordered by `sort_order`.
- **Score (user's rule, `FitScore`, computed in code, not by AI; reworked 2026-10-21):** 경력/학력 met = 1, not met = 0; a condition the posting doesn't state = 1; info missing from the resume = 0 (education: `required_education` blank = no condition, otherwise only `MET` counts; a failed EDUCATION_EVAL = 0). Each criterion: DIRECT 1, INDIRECT 0.5, NONE 0, all equal (per-criterion weights and a 100-point scale were tried and removed by the user). Max = 2 + criteria, shown as "7.5 / 8". The 지원자 비교 toggles 경력 미충족 제외 / 학력 미충족 제외 (`position.exclude_career`/`exclude_education`, `PATCH /positions/{id}/exclusions`) move those candidates unranked into a folded "제외됨 n명" group (`RankingRow.exclusion`, state EXCLUDED) below the ranked ones. **Salary is not evaluated at all (user, 2026-10-21):** it is only masked; no salary stamp, chart, score, ranking column or posting salary condition. Ties: more DIRECT, then longer relevant career. A candidate checked before the criteria changed (some criterion has no evidence) is "재검사 필요" and is listed unranked below the ranked ones, then unchecked candidates.
- **포지션 적합도 검사 (1인) / (다수) (user):** 1인 is the upload → review → check flow below. 다수 (`/fit?position=..&mode=batch`, `POST /positions/{id}/batch`, `BatchCheckService`): one drop zone per applicant (`applicant-1`, `applicant-2`…; a zone may hold resume + portfolio; dropping several files on "지원자 추가" fills one zone per file), then one button runs masking → fit check for each applicant in turn on a single background thread. No human review (user accepted): an applicant whose masking fails or leaves an RRN/phone/email shape becomes FAILED and never reaches GPT. Interview questions are never generated in bulk; the interviewer picks whom to generate for. Raw text lives only in memory until masked, so `QUEUED`/`MASKING`/`ANALYZING` candidates are set to FAILED at startup (`failUnfinished`). The fit page polls `GET /positions/{id}/candidates` every 3 s while anyone is in progress and reloads when the viewed candidate's status changes.

- **UI taste (user):** use the full width, keep it simple, no explanatory helper text or minor stats. Theme (2026-10-21 redesign, user found the old one plain/ugly): warm paper background, white cards with hairline borders and almost no shadow, one deep pine-green `--accent`, 15.5px base type, 60px top bar; the 지원자 비교 grid uses ●◐○ circles instead of boxed numbers; neutrals come from tokens (`--hover`, `--chip`), not hard-coded greys. Muted data tones (`--data` dusty blue, sage, ochre, warm grey); no indigo/purple or gradients (the user found them tacky and "AI-looking"). Stamps stay red = 충족, blue = 미충족.
- **Position files:** `PositionService.create` takes images, PDFs and .txt/.md (max 5). PDF/text content is appended to `jd_text` under a `[filename]` line; a PDF with almost no text (scanned) is rendered to PNG pages (`PdfTextExtractor.renderPages`) and treated as images. **Position images** live in `position_image` (BYTEA, type sniffed from bytes, not the upload header). AI ① gets them as `image_url` data-URL parts via `AiClient.call(..., images, ...)` and returns `image_text`, stored in `position.image_text`; later steps read `Position.getPostingText()` (text + image text).
- **Common questions have no kind (FIXED/COMMON/NOTICE) and sections are user-defined** (`question_section`: create, rename, delete, drag to reorder). Every template question may be personalized by AI ③; unrelated ones stay verbatim. The legacy `question_template.section`/`kind` columns remain only for migrating old data in `data.sql`.
- **Database:** PostgreSQL 17 instead of MySQL. Tests run on H2 in `MODE=PostgreSQL`, so `schema.sql` must stay valid in both.
- **AI provider:** an OpenAI-compatible Chat Completions API instead of the Claude Messages API. The provider is chosen only by `ai.base-url` and `ai.model`.

## Commands

Gradle wrapper; Spring Boot 4.1, Java 17. On Windows use `.\gradlew`.

```
./gradlew test                                   # all tests (H2, no DB server or API key needed)
./gradlew test --tests "*PiiMaskerTest"          # single class
./gradlew test --tests "*PiiMaskerTest.labelsByType"
./gradlew bootRun                                # needs PostgreSQL + Ollama + secrets below
./gradlew build                                  # executable war -> build/libs/interview-0.0.1-SNAPSHOT.war
```

The app listens on port 8090; the DB defaults to `jdbc:postgresql://localhost:5432/interview` (override with `DB_URL`, `DB_USERNAME`). Secrets come from env vars (`DB_PASSWORD`, `AI_API_KEY` or `OPENAI_API_KEY`, `AI_MODEL`, `AI_BASE_URL`) or from the gitignored `config/application-local.properties`, which `application.properties` imports when present. Resume upload also needs a local Ollama (`local-ai.*`, env `LOCAL_AI_BASE_URL` / `LOCAL_AI_MODEL`, default `http://localhost:11434` + `gemma4:e4b`; run `ollama pull gemma4:e4b` once). Never put secrets in tracked files. Optional: `ai.input-price-per1m` / `ai.output-price-per1m` for cost display.

`SameOriginFilter` rejects non-GET requests whose `Origin` host differs. A desktop app (jpackage + H2) was tried on 2026-10-21 and dropped by the user; there is no settings page, the API key comes only from env vars or `config/application-local.properties`.

`./gradlew test` writes Korean sample resume PDFs to `build/sample-resumes/` for manual upload testing. `measurement.sql` has the presentation metric queries.

## Architecture

Request flow: `controller/` → `service/` → `mapper/` (MyBatis interfaces + XML in `resources/mapper/`). JSPs live in `src/main/webapp/WEB-INF/views/` and share the `common/header.jspf` / `footer.jspf` static includes. Each page sets `activeTab` before including the header.

**Flow** (`ExtractController`, `static/js/extract.js` on `positions.jsp` and `fit.jsp`). URLs: `/positions` (new position), `/positions/{id}` (criteria), `/fit?position={id}` (resume upload), `/results/{id}` (candidate id; evidence + questions), `/ranking?position={id}`.
1. `POST /positions` → `PositionService.create` + `extractCriteria` (AI ①; sets the title from `position_title`, stores the posting's `required_experience` and `required_education` verbatim (empty string from the AI = absent, stored as null), marks CONFIRMED; criteria never carry years or education, e.g. "Java/Spring 기반 개발 경험" not "5년 이상", because the stamps compare those and AI ② once listed "총 2년 3개월" as DIRECT evidence for a 5-year criterion, which scored it full; `evidence.txt` also says to judge no years and to list only supporting evidence); the user can rename a position in place (pencil next to the title or on each list item on hover, `PATCH /positions/{id}`), which sets `position.title_edited` so a later re-extraction no longer overwrites the name. 경력·학력 conditions are always shown above the criteria (empty = 공고에 없음) and edited together with the pencil through dropdowns, not free text, per the user (경력: 공고에 없음/경력무관/N년 이상/N년 이하; 학력: 학력무관/고졸/초대졸(2·3년제)/대졸(4년제)/석사/박사 이상). `ConditionForm` reads the stored wording into the initial choices; the page saves fixed wording ("경력 3년 이하", "대졸(4년제) 이상") with `PATCH /positions/{id}/conditions` (blank = no condition). "N년 이하" is a cap (`CareerGauge.meets`); that sets `conditions_edited` so re-extraction keeps them. EDUCATION_EVAL gets `position.required_education` as `<education_requirement>` (blank = no condition; the posting text is not sent); the career stamp reads the position field directly, so only the education stamp needs a re-check after an edit. Both are shown above the criteria and in the stage-② profile band. Criteria CRUD is JSON fetch under `/positions/{id}/criteria`.
2. `POST /positions/{id}/resume` → `ExtractionService.uploadResume`: takes any number of files (resume + portfolio; PDF, DOCX, PPTX, HWP, HWPX via `DocumentTextExtractor`; no count limit, only the per-file and request size limits). Every file is read before any AI call (a bad file saves nothing). With more than one file, texts are joined under `[첨부 n (형식)]` lines; file names are never put in the text because they often contain the applicant's name. Then `ResumeAnonymizer` splits the text into line-based chunks of `CHUNK_CHARS` (halving a chunk again if Ollama reports truncation), the local AI (Ollama, PII_DETECT, `pii_detect.txt`, thinking on) fills one fixed form per chunk (`PiiExtract`, below), `PiiMasker` replaces every occurrence of every value in it in the whole text, and `PiiLeakChecker` rejects the upload if an RRN/phone/email shape is still there. If the local AI fails or a leak is found, nothing is saved and the raw text never reaches the external AI (only `masked_text` is stored). Upload stops there and makes no external AI call: it creates a `candidate` in UPLOADED (shown as the review editor, `initReview` in `extract.js`: drag to mask every occurrence as `[개인정보]`, 되돌리기 undoes the user's own masks; chips are plain labels (the user found click-to-type pointless) and the original is never kept, so there is no unmask; instead, per the user, 직접 고치기 turns the view into the plain textarea (labels as text) for free editing, and 고치기 끝 goes back to chips with one 되돌리기 step). `POST /results/{id}/check` with `maskedText` re-runs `PiiLeakChecker`, saves the reviewed text, then `ExtractionService.checkFit` runs two external calls in parallel: `AnalysisService.analyzeEvidence` (AI ② + `QuoteVerifier`; replaces evidence and drops questions; the same call returns total and position-relevant career) → ANALYZED, and the resume-less EDUCATION_EVAL and TIMELINE calls below (three calls at once, per the user). Only the masked text is shown before the check; the profile band (인적사항, career, education, timeline) renders only once `fitChecked`, per the user. Without `maskedText` it re-checks the saved text. Per the user, the review editor always stays at the top of stage ② (its button reads 다시 검사 after a check, and editing then re-checking replaces the results), with the results below it; there is no separate "다시 검토" step. Right after a check the controller sets the flash attribute `justChecked`, which plays the 충족/미충족 badge pop-in once (pill badges with a ✓/✕ dot next to the card labels 경력/학력; round overflowing stamps and an ink-stamp look were tried and rejected by the user). One position has many candidates (the chips in stage ②). Candidates are renamed from the pencil on their list item (`PATCH /results/{id}`, `CandidateService.rename`; refused while QUEUED/MASKING/ANALYZING because batch masking writes the detected name; the page updates every `data-cand-name` element).
3. `POST /results/{id}/questions/generate` → `AnalysisService.generateQuestions`: two AI calls. ③-1 `QuestionService.generate` (QUESTION, `questions.txt`) extracts criterion-verifying questions with no section or order. ③-2 `QuestionService.arrange` (ARRANGE, `arrange.txt`) gets the common questions by section plus the extracted ones and returns the final sections and order, personalizing common questions on the way; section names may be new. `ArrangeResult.validate` rejects only unknown or duplicate ids; whatever the AI left out is filled in by `QuestionSheetAssembler` next to its neighbors (a common question beside its configured-section neighbor, or as its own section after the previous one; an extracted question after one with the same criterion). Unchanged common questions are returned as `{template_id}` only, to keep the output short (long outputs made the model drop items). Then `QuestionSheetAssembler` → DONE. Question CRUD/reorder is JSON fetch under `/results/{id}/questions`; `reorderQuestions` rejects stale boards.
4. AI failures don't throw to the controller: the candidate becomes FAILED with `error_message`; the stage whose data is missing shows the error and a retry. Criteria added after a check show as "검사 전" (no evidence rows) until re-checked (`POST /results/{id}/check`). AI ① can be re-run with `POST /positions/{id}/criteria/extract`.

Deleting a position cascades its candidates; deleting a candidate keeps the position.

**Common question settings** (`TemplateController` + `static/js/templates.js`): the page renders once, then every edit is a JSON `fetch` (`X-Requested-With: fetch`). Drag-and-drop sends the whole board to `PUT /templates/order`; `TemplateService.reorder` rejects stale boards (every section and question must appear exactly once). AI ③-2 sees the configured sections as a suggested flow but may rename, merge or add sections. `interview_question.section` stores the section *name* at generation time, so later edits don't change past results.

**Result screen and PDF** both come from `fit.jsp` (`ReportService.report(id)` → `ResultReport`). There is no server-side PDF: the PDF button saves pending answers and calls `window.print()`, and `@media print` in `app.css` hides the tabs, position picker, candidate list, review editor and all controls so the PDF looks like the screen. Keep layout media queries `screen`-only. Answers autosave via `fetch` to `POST /results/{id}/questions/{qid}/answer` with header `X-Requested-With: fetch`; the question number is a toggle for "asked" (`interview_question.checked`, `POST .../{qid}/checked`), and saving a non-empty answer also checks it (user); `GlobalExceptionHandler` returns plain-text errors for those requests instead of redirecting.

**Rules to preserve:**
- **View models used from JSP must be classes with getters, not records.** Tomcat 11's EL exposes only record components, so derived getters like `getMatch()` would be invisible. That's why `ResultReport`, `CriterionEvidenceView`, `SectionView`, and `QuestionView` use Lombok `@Value`.
- **AI calls stay outside DB transactions.** Only DB writes are wrapped in `TransactionTemplate`.
- **`AiClient` is the single entry point for all AI calls.** `call` goes to the external OpenAI-compatible API; `callLocal` goes to Ollama's native `/api/chat` (OpenAI-compatible mode can't set `num_ctx`, so long resumes would be silently cut; a call that reaches `num_ctx` fails).
  - It strips code fences, parses JSON with Jackson 3 (`tools.jackson.*`), and runs the DTO's `validate`.
  - It retries **exactly once** with the error appended, then throws `AiCallException`.
  - Every attempt is logged to `ai_call_log` via `AiCallLogger`, which uses `REQUIRES_NEW`.
  - The `ai.trace` logger (user request) prints every GPT and local AI request (`[GPT 요청]`, `[로컬 AI 요청]`: all messages; images only as a count) and response, pretty-printed, to the console. Local requests and responses contain the raw PII. `logging.level.ai.trace` turns it off (OFF in tests).
  - The user pays for GPT: verify with stubbed tests or local-only runs, and make real GPT calls only when truly needed.
- **Evidence IDs sent to AI ③ are 1-based list positions** in the saved evidence list. `AnalysisService.generateQuestions` maps them back to real IDs. The assembler drops unknown IDs instead of guessing.
- **Question sheet order (initial):** the ③-2 arrangement plus the gap filling above; "기타" is used only when there is no anchor at all. After that the user can reorder freely. `origin=FIXED` only exists in old rows and is shown as 공통; `MANUAL` is a user-added question.
- **Prompts are files** (`resources/prompts/*.txt`), read on every call.
  - Untrusted input is wrapped in tags (`<resume>`, `<job_posting>`, …) and declared as data, not instructions.
  - The candidate's name and unmasked resume text are never sent to the external AI.
- **Hidden vs. sent (user's rule).** Never sent to the external AI: name, age, gender, contact, email, address, links, employer, rank, salaries, education, desired salary, training, certificates. Sent (evidence): career periods (재직 기간, 근무 기간, 총 경력; unmasked since 2026-10-21 per the user, because AI ② needs them for the career count and they were sent anyway), work/project content and results, tech stack, project names and dates, client companies, team names, cover letter. Labels: `[이름] [전화번호] [이메일] [주민번호] [링크] [생년월일] [주소] [개인정보] [회사] [A사] [B사]… [연봉] [경력] [학교] [학력] [교육] [자격증]`. `evidence.txt` tells AI ② to mark criteria that need hidden facts (degree, certificates, training) as NONE and point to the summary at the top. Exception, also the user's rule: the career/education calculation call (below) sends tenure periods, team names, school names and school status, but never company names (they become "A사", "B사"), rank, salary, major or GPA. Salary text is never sent in any form (the 2026-10-20 SALARY_NORMALIZE exception was removed with salary evaluation).
- **PII masking is done by the local AI; regex is only a backstop.** `ResumeAnonymizer.normalize` first turns PDF special spaces (U+00A0 etc.) and full-width ASCII into plain characters; without it, Java `s` misses NBSP and values like "3,400 만원" never match. (Not NFKC: it would rewrite Korean compatibility jamo like "ㆍ".) `PiiExtract.validate` fills missing fields with empty values and never fails, and swaps a career's 재직 기간 and 근무 기간 when only the latter holds a date (gemma4 mixed them up; the prompt also gives examples now). `PiiMasker` matches every value ignoring whitespace and case, because the model often re-spaces what it copies ("3,400만원" vs "3,400 만원"). `ResumeAnonymizer.LABELED` covers fixed shapes the model misses intermittently: age, the postal code after "주소", the date after "생년월일", the rest of a "주소" line starting with a 시·도 name, amounts after "연봉", GPA, "대학교(4년)"/"(2·3년제)", the "인정학력" line, and the value after a 장애/보훈/병역 field ("병역 : 군필", "장애여부 해당 없음"; a bare label needs a colon so prose like "병역 특례 업체" is untouched; military-table values written with spaces only: service status and type words (병역필, 군필, 만기제대, 의무경찰, 사회복무요원…) anywhere, ranks after 계급 or in parentheses ("수경(병장)"), the value after 군별/역종/병과/주특기/군번/제대·전역·복무 구분 (label followed by a space or colon, so "특기사항", "주특기는" stay) and a same-line 면제 사유). Age/birth date/address/salary values are masked everywhere; the education patterns and the 장애·보훈·병역 values are masked only where they match (`maskLabeled`, after value masking so the full address still matches first). `PiiLeakChecker.maskObvious` then masks any RRN/phone/email shapes still left (the local AI intermittently misses a second number such as an emergency contact), and `find` rejects leftovers (after NFKC normalization; it is also the check on user-edited text at the review step). The resume text goes only to the local AI before masking.
- **Profile (인적사항·경력·학력·교육·자격증) is shown, never sent.** **One form, no stated purpose (user, 2026-10-21):** the local AI is only asked to find and copy values into Korean-keyed fields (`PiiExtract`: 이름[], 다른 사람 이름[], 성별, 생년월일[], 연락처[], 이메일[], 주소[], 링크[], 학력[{학교,전공,상태,기간,학점}], 경력[{회사[] (every spelling), 부서, 직급, 재직 기간, 근무 기간}], 총 경력, 연봉[], 교육[], 자격증[], 활동[], 기타 개인정보[]); the prompt never mentions masking or what may be sent. The earlier prompt asked for "items to mask" plus a "profile", and gemma4 read it as "filter sensitive values out" and left both nearly empty (only the name), leaking companies, school, email and link. Code derives both uses: `PiiExtract.toItems()` masks every value except the department and career periods (재직 기간, 근무 기간, 총 경력; rank is still masked as `[경력]`; activities only for 병역), `toProfile()` builds the display profile (first spelling of each single field, no salary). `ResumeAnonymizer` merges chunks, drops profile values not found in the original text (whitespace-insensitive). `anonymize` runs five steps in order: 1) detect and merge (profile verified), 2) `byCompany` + `aliasCompanies`, 3) `maskList` (every found value, company names also without "(주)"-style legal forms, companies labeled by alias), 4) mask, 5) return for saving. `byCompany` folds careers of the same company into one row (first non-empty value per field, so the summary table's period wins over the per-project 근무기간 blocks of a 경력기술서). `aliasCompanies` then stores `alias` ("A사", "B사"… in career-list order) on each career and masks each listed company (with and without its legal form) as `[A사]`, `[B사]`…; every external call and `TimelineView` use that stored alias, so the external AI can tell which work belongs to which company; other spellings of the same company (`PiiExtract.companyNames`) get the same letter, and any other company label stays `[회사]`. In the same step `aliasOthers` stores `alias` "학교1", "교육1", "활동1" (list order) on education, trainings and activities (user, 2026-10-21: every alias is saved with the profile, none is derived at request time; old profiles without aliases are not supported and the DB was reset). The review editor's label regex in `extract.js` knows these labels. It is stored as `candidate.profile_json` (so contact details are in our DB) and shown read-only in stage ② after the fit check and in the PDF, next to the posting's required experience. The profile also has `activities` (병역, 연수, 인턴, 회사 밖 프로젝트: kind + name + period, for the timeline; only 병역 values are added to the mask list). Keep `pii_detect.txt` short: a longer activities instruction once made gemma4 drop birth/address/phone/email in 4/4 runs. **Salaries are masked but not kept (user, 2026-10-21):** PII_DETECT copies every salary into 연봉[] so it is masked (with the SALARY `LABELED` patterns as backstop), but `toProfile` never puts salaries in the profile. Old profiles may still hold salary values; nothing reads them. (A separate SALARY_EXTRACT local call existed briefly and was removed with salary evaluation.) The `ai.trace` log prints every local call's `thinking` as `[로컬 AI 생각]`. gemma4:26b was tried on 2026-10-20: one chunk took 4m40s, filled `num_ctx` 8192 with thinking and returned nothing, with RAM at 98%; e4b stays. **Career/education calculation (both at the fit check, user's split):** total career needs the resume body (the user treats "총 경력" as position-relevant), so AI ② (`evidence.txt`) gets only `기준 월`, the posting (for the job type), the criteria (id, name, description) and the masked resume, where periods are visible next to `[A사]` (no separate career list and no required-experience line, per the user), and returns `career` (per_company first, then total months with overlaps counted once and relevant months; `EvidenceResult.validate` requires it). Two parallel resume-less calls replaced the single CAREER_EVAL (user, 2026-10-21; the enum value stays only for old log rows): EDUCATION_EVAL (`education_eval.txt`, `CareerEvalService.education`, reasoning model) sends only "학교명 | 상태 | 기간" lines and the position's `required_education`, and returns `final_education`, `education_reason`, `education_meets` (skipped when there are no schools; forced to UNKNOWN when there is no condition); TIMELINE (`timeline.txt`, `CareerEvalService.timeline`, default model) sends only `기준 월` and "A사 / 학교1 / 교육1 / 활동1 | 기간" lines (no names or activity kinds) and returns each label → YYYY-MM start/end (unreadable ones are dropped, not failed). Prompts are kept as short as accuracy allows (user). `CareerEvalService.save` merges all three into `CareerEvalResult`; a failed call keeps its previously saved fields. `TimelineView` maps the stored aliases back to real names, sets a minimum px width for the time axis so each label fits inside its bar (estimated from character widths, capped at `MAX_WIDTH`; the card scrolls horizontally and starts scrolled to the latest records, per the user who disliked cut-off "…" labels), puts the label beside any bar still too short, stacks overlaps including those outside labels, and marks months covered by nothing for 3+ months between the first record and today as "이력서상 기록 없음" (computed in code). All five lanes (경력·학력·교육·활동·기록 없음) are always shown, empty ones too (user wants it consistent). In the PDF the chart is hidden and the same items print as a plain list in start order regardless of lane (`TimelineView.getEntries`, `.tl-list`, user's choice after a vertical-axis attempt was rejected). The user wants the external AI, not code or the local AI, to do the career arithmetic and judgment. EVIDENCE and EDUCATION_EVAL use `ai.reasoning-model` (default gpt-5-mini, env `AI_REASONING_MODEL`; `AiProperties.modelFor`) with `ai.reasoning-max-tokens` (default 25000, since reasoning tokens count toward the cap; non-reasoning models such as gpt-4o-mini reject anything over 16384): in a 2026-10-19 comparison on fictional cases only reasoning models got the overlap arithmetic right (gpt-4o-mini 7/12, gpt-4.1 3/12, gpt-5-mini 12/12). On a real resume on 2026-10-20, gpt-5-mini's evidence quotes were 12/12 verbatim (≈47 s) vs gpt-4o-mini 3/6 with a missed AWS mention (≈6 s). The prompt makes it fill `per_company` first, which made the relevant-months judgment stable. **충족/미충족 stamps** (user request; per posting condition, not a hire decision): `RequirementFit` — career = relevant months (total before the check) vs the posting's years, 무관/신입 = met; education = `education_meets` from EDUCATION_EVAL (the position's `required_education` is stored next to it). Red = 충족, blue = 미충족. It is stored in `candidate.career_eval_json`; a failure only leaves it null. `CareerGauge` draws total (light) and relevant (dark) career against the posting's years read by regex ("3~5년" → lower bound, 신입/무관 → no marker); before the check it falls back to the resume's verbatim total career.
- **JSP output escaping:**
  - Static JS/CSS URLs carry `?v=${applicationScope.assetVersion}` (server start time, `AssetVersionConfig`) so a restart never leaves the browser on old scripts; add it to any new script or stylesheet tag.
  - Escape all user and AI text with `<c:out>`.
  - Each `.jspf` needs its own `pageEncoding="UTF-8"`.
  - Session tracking is cookie-only, so URLs never get `;jsessionid`.
- **Test properties replace the main ones.** `src/test/resources/application.properties` fully shadows the main file, so add new required properties to both. Schema changes to existing tables go in `schema.sql` as idempotent `ALTER TABLE` statements valid in both PostgreSQL and H2; one-time seed data is guarded by `app_setting('seeded')` so deleted defaults don't come back.

**Out of scope:** login, formats other than PDF/DOCX/PPTX/HWP/HWPX (old .doc/.ppt included), text inside images (OCR), AI-made scores or hire decisions (the score is code arithmetic over the stamps and evidence), parallel batch analysis or batch question generation. Test only with fictional resumes.
